# SY0-701 objective 1.3: Change management and security

[Security+ index](../../README.md) · Domain 1: General Security Concepts

These are original study notes aligned to the public CompTIA SY0-701 V7 exam objectives, not official CompTIA training or exam questions.

## Explain it

A controlled change has an owner, request, rationale, impact and dependency analysis, test evidence, approval, implementation window, communications, and a backout plan. The process makes changes traceable and limits unplanned outages or exposure. A standard low-risk change may use a preapproved path, while an emergency change is expedited but still documented and reviewed afterward.

Technical planning includes possible downtime, service restarts, legacy incompatibility, version control, configuration baselines, and updated diagrams or procedures. Test both the intended effect and side effects. A rollback plan should specify trigger, responsible person, steps, and how service restoration will be verified. Record post-change results and any new risk; approval to deploy is not evidence that deployment succeeded.

Security teams should examine firewall rules, identity permissions, certificates, and logging changes in particular because small configuration errors can widen access or blind monitoring.

## Deeper distinctions

A change ticket should connect a **baseline before**, **approved intended state**, and **observed state after**. Scope the impact on users, dependencies, security controls and recovery. Separate the person proposing the change from approvers where risk warrants; emergency implementation may occur before the usual meeting, but it still requires an accountable authorization and retrospective review.

Tests should include functional success, security regression and rollback rehearsal where practical. A maintenance window reduces disruption but does not itself reduce misconfiguration risk. Update diagrams, asset inventory, runbooks and detection rules when a change alters data flow or ownership. Version control makes the configuration diff and prior state recoverable; a successful deployment record alone cannot prove the resulting access is appropriately narrow.

**Decision drill:** A certificate renewal unexpectedly breaks a dependent service. Before trying random settings, verify the chain, hostname and validity; inspect the change record and dependencies; restore service through the approved backout while preserving evidence for cause analysis.

## Additional blueprint concepts

Change impact is not limited to outage duration. An allow-list edit may open new paths; a deny-list edit may block a critical workflow. A restricted activity, service restart or application restart may interrupt monitoring or dependent systems. Record stakeholders and ownership, test results, updated diagrams and procedures, and a versioned configuration so the approved change can be compared with the deployed state.

## Apply it

A proposed firewall exception opens a management port to a vendor. Require a narrowly scoped source, owner, expiration, test, approval, monitoring, and rollback; compare the actual rule with the approved request afterward.

## Active recall

Describe the evidence you would expect in a change ticket before and after deployment. What makes an emergency change accountable?
